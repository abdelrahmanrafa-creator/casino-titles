# Casino & Titles

Nouveau site autonome créé le 22 octobre 2026. Aucun import du code, aucune économie, aucune session de joueur historique du casino parent. Le projet possède son propre package, sa compilation, ses tests et son dépôt Sites. Supabase reste le projet connecté existant, avec des tables `ct_` isolées et de nouvelles identités Supabase Auth ; ce n’est pas un second projet Supabase.

## Démarrer
`npm ci`, renseigner les deux variables publiques décrites dans `.env.example`, puis `npm run dev`. URL locale : http://127.0.0.1:5180. `npm test` exécute les tests PostgreSQL et les moteurs multijoueurs ; `npm run build` vérifie TypeScript strict et produit `dist/`. Déploiement Vercel prêt via `vercel.json` ; la publication Sites conserve son identité dans `.openai/hosting.json`.

## Architecture
- React, Vite, TypeScript strict, Tailwind, React Router, TanStack Query, Framer Motion et Lucide.
- Auth géré par Supabase, jamais de comparaison de mot de passe dans le navigateur. E-mail confirmé requis pour créer un profil.
- PostgreSQL : contraintes, RLS, commandes métier SECURITY DEFINER au search_path fermé ; aucune écriture du client sur le portefeuille, le journal ou les états privés des jeux.
- Une commande économique = une transaction, verrou du portefeuille, clé d’idempotence UUID par joueur, reçu, journal et changement métier.
- Le journal indique montant, solde après et version. Son total est réconcilié avec chaque portefeuille par `supabase/verify.sql`.
- Les commandes interrompues conservent seulement leurs identifiants et paramètres dans le navigateur. La reprise réutilise la même clé ; aucun solde ou résultat local n’est considéré comme valide.
- Limite de 30 nouvelles commandes validées/minute/compte ; les relectures d’un reçu restent possibles. Les échecs annulés ne consomment pas le compteur transactionnel. La protection volumétrique en amont et le débit Auth relèvent aussi de Supabase et de l’hébergeur.
- Multijoueur : Edge Function `ct-tables`, vérification du JWT via Auth `getUser`, moteur autoritaire, écritures réservées au service, révisions optimistes et séquestre transactionnel. Realtime ne transporte que l’identifiant du salon et sa version. Les réponses masquent le paquet et les cartes adverses. Rafraîchissement de secours toutes les cinq secondes.

## Backend et déploiement
Les migrations de ce dossier ont été appliquées au Supabase connecté et la fonction `ct-tables` y est déployée. Sur un nouveau projet, appliquer uniquement ces migrations dans l’ordre des noms, puis déployer `supabase/functions/tables`. Les rôles standards Supabase doivent exister. Le script de création des salons fait référence aux suspensions ; ne pas ouvrir le site avant d’avoir terminé toutes les migrations.

Dans Supabase Auth, conserver la confirmation d’e-mail et autoriser l’origine déployée ainsi que http://127.0.0.1:5180 dans les URL de redirection. Le connecteur disponible ne permet pas de modifier ces paramètres Auth. Un e-mail de confirmation doit être testé de bout en bout avant une ouverture générale. Le flux de récupération utilise `/settings`.

La console est `/admin`, sans lien dans la navigation publique. Son accès exige un compte confirmé, un rôle administrateur attribué côté serveur. Une fois activé, le compte connecté accède au panneau sans ressaisir le code. L’activation initiale unique se fait avec le code généré dans `.admin-access.local.txt`, exclu de Git et de la publication. Aucun premier inscrit ne devient administrateur sans ce code. Voir `ADMIN_GUIDE.md`.

## Validation et limites de recette
84 tests automatiques passent : paiements, permissions, restauration physique locale, coffres, combinaisons poker, pots secondaires, cartes privées, règles du Blackjack/Baccarat, missions, événements, révocation, paramètres, offres, stocks, sessions administrateur, rotation du code et affichage du prix barré. PGlite sérialise les transactions ; les tests locaux ne prouvent pas seuls le comportement de connexions PostgreSQL concurrentes.

Une recette supplémentaire sur le Supabase hébergé a utilisé une identité synthétique sans adresse e-mail ni mot de passe, supprimée après les tests : deux demandes quotidiennes concurrentes ont versé une seule récompense ; douze ouvertures concurrentes avec 5 750 crédits ont produit exactement onze titres, onze historiques et un solde de 250. Les douze assertions de `supabase/verify.sql` passent sur l’hébergement.

Contrôle visuel effectué dans le navigateur intégré sur une largeur mobile : accueil, coffres, probabilités et album réel. La compilation ne remplace pas la recette de deux navigateurs authentifiés : inscription/e-mail, Realtime entre deux utilisateurs, perte de connexion et charge prolongée restent à valider sur l’hébergement avant de qualifier le multijoueur de prêt à grande échelle. Les timeouts sont traités par le serveur à la synchronisation ou à la reconnexion ; il n’y a pas de tâche planifiée autonome quand tous les clients sont fermés.

Les règles du Blackjack sont configurables côté administrateur : S17/H17, paiement naturel 3:2 ou 6:5, deux à quatre mains, double après séparation. Leur version est fixée au début de chaque manche et ne peut changer une manche en cours. Les classements de victoires concernent les parties solo. Les modes publics sont sans vrai argent ni conversion. Les sauvegardes hors site et PITR ne sont pas activées automatiquement : voir `BACKUPS.md`.

Le contrôle Supabase relève aussi des alertes sur les anciennes tables du projet parent. Ce nouveau site ne les utilise pas et ce travail n’a pas modifié leurs politiques. Les nouvelles tables privées sans politique de lecture sont volontairement fermées ; les RPC publiques de classement/profil ne renvoient que leur projection publique.

La collection propose un album par rareté, filtres de découverte, fiches et exemplaires. Les titres Rainbow, Xtrem et Cosmiques non possédés sont masqués visuellement (nom, description et source) et la recherche utilise uniquement le nom révélé. Ce masquage concerne l’album, pas la confidentialité du catalogue public ni les titres affichés sur les profils des autres joueurs.

Les codes se partagent depuis l’équipe, ils ne sont pas publiés dans un catalogue accessible aux joueurs.

La recherche de pseudos est disponible sur l’accueil et les classements (2 caractères minimum, 30 résultats au maximum). Les profils affichent les titres actuellement possédés et leurs exemplaires, sans journal financier ni données Auth. Les cartes de collection affichent le nombre de détenteurs distincts, hors titres révoqués et comptes suspendus. Le compteur est rafraîchi toutes les 60 secondes.

Les sept jeux ont des explications supplémentaires ; les jeux solo affichent des exemples de retour mise comprise, des mises rapides et les limites administrateur. Les lignes gagnantes des Slots sont mises en évidence. L’aperçu de l’atelier et des guides a été vérifié visuellement sur des données de test. Les parcours complets dans le navigateur avec un véritable compte connecté restent à compléter ; les transactions ont été testées dans PostgreSQL local et les endpoints publics sur l’hébergement (19 contrôles réseau).

## Confidentialité des classements et coffre-fort
Dans Paramètres, chaque joueur peut masquer son compte de toutes les catégories du classement permanent et hebdomadaire. La préférence est enregistrée côté serveur et filtrée avant la limite de cinquante résultats. Les profils, la recherche de pseudo, les soldes et les statistiques globales restent inchangés.

Administration → Économie & coffre-fort affiche les crédits disponibles du serveur, les portefeuilles des joueurs, les crédits réservés aux tables, les flux quotidiens sur 7/30/90 jours, les totaux par origine et un journal paginé. Le capital initial virtuel est de 100 000 000 crédits. Une contre-écriture de montant opposé est créée par trigger dans la transaction de chaque mouvement du portefeuille, y compris la prime initiale de 5 000 crédits, les promotions et les ajustements administrateur. Le solde du coffre-fort est calculé depuis ce journal ; aucun verrou global supplémentaire ne sérialise les portefeuilles. Les entrées multijoueurs sont déduites du disponible tant que les tables ne sont pas réglées. La suppression d’un compte restitue son solde et conserve les traces comptables.

Le coffre-fort est un suivi comptable virtuel : un déficit éventuel apparaît explicitement sans bloquer un gain dû. Le capital total reste coffre-fort disponible + réservations + portefeuilles. La migration `20261022190000_treasury_privacy.sql` est appliquée sur le Supabase hébergé, avec reprise des transactions historiques. Les huit assertions de `supabase/verify-treasury.sql` passent sur ce serveur. La compilation et 84 tests automatiques sont complétés par dix-neuf contrôles réseau. L’aperçu visuel du coffre-fort utilise des données de recette identifiées.

## Comptes bots figés
Administration → Bots permet de préparer des lots de 1 à 25 comptes simulés (jusqu’à 5 000 au total), prévisualiser et modifier les pseudos, choisir un style de noms, répartir exactement les meilleures raretés, sélectionner les titres éligibles, définir les soldes et générer des historiques. Les styles incluent des pseudos réalistes, plus de 200 mots anglais, trois lettres, trois chiffres (zéros initiaux conservés), trois caractères mixtes et des pseudos de jeu.

Chaque bot est un profil `is_bot=true` sans compte Auth ; les comptes humains conservent leur lien Auth, leur inscription et la suppression en cascade. Les titres sont de vrais exemplaires dans l’inventaire. Les ouvertures et parties sont enregistrées avec `simulated=true`, sans prétendre avoir été jouées par un humain. Les séries Coinflip ont un nombre de victoires égal à la partie entière du taux configuré, réparti aléatoirement. Les probabilités des coffres simulés reflètent la collection autorisée du bot, sans utiliser les stocks ou promotions destinés aux joueurs. Aucun titre Cosmique, y compris par attribution administrative ou reclassification d’un titre existant.

Le financement, les achats, mises, gains et ajustements sont intégralement inscrits dans le journal et compensés dans le coffre-fort. L’excédent de financement est restitué : le coût net de création est exactement la somme des soldes finaux des bots. Les comptes ne peuvent ni se connecter, ni réclamer des récompenses, ni rejoindre les tables multijoueurs, ni devenir administrateurs. Aucun ordonnanceur ou comportement autonome n’est installé. Les dates restent celles de la création du lot.

Les profils, résultats de recherche et classements signalent les bots ; les statistiques de détenteurs précisent leur nombre. Les soldes humains ne sont pas ajoutés aux profils publics. L’édition est protégée contre les modifications concurrentes ; archiver conserve l’argent et les historiques mais masque le profil et les classements. Pour rendre ses crédits au coffre-fort, l’administrateur peut régler le solde du bot à zéro. La création est atomique et idempotente ; le budget de travail est limité à 4 000 unités par requête.

La migration des bots est appliquée au serveur. Une création complète, le gel, les statistiques et le coffre-fort ont été vérifiés dans une transaction hébergée annulée : aucun bot de recette ne reste en production. Les huit tests dédiés et les tests d’interface/génération de noms passent dans une suite de 84 tests. Les contrôles de `supabase/verify-bots.sql` complètent les vérifications économiques.

## Coffres en réserve, récompenses et échanges directs
La boutique propose « Acheter pour conserver » vers les coffres scellés au tarif standard. Les coffres restent dans Inventaire : ouverture différée sans surcoût, vente contre des diamants ou échange contre un objet depuis le marché noir. Les coffres à stock fini et les événements restent disponibles en ouverture immédiate. Les probabilités et le catalogue éligible sont figés au moment de l’acquisition du coffre scellé.

Trois missions offrent maintenant un coffre (création du profil, cinq titres uniques, dix parties solo). Administration → Jeux & missions et Codes promo permettent de choisir un coffre standard éligible, entre un et cinq exemplaires, seul ou avec des crédits/titres. La distribution, l’historique de réclamation et le reçu idempotent forment une transaction unique. Une récompense indisponible ne consomme pas la réclamation.

Le bouton Échanges en haut du site permet d’inviter un pseudo exact. Après acceptation, une fenêtre s’ouvre chez les deux joueurs : chacun propose jusqu’à dix exemplaires de titres/coffres et un montant de diamants. Chaque changement de proposition incrémente sa version et annule les deux confirmations. Les réservations empêchent une ouverture, une mise en vente, un équipement ou une dépense concurrente. Les deux confirmations portent sur la même version ; les deux offres sont transférées ensemble et le reçu est conservé côté serveur. Annulation/refus/expiration libèrent les objets et diamants. Invitations valables quinze minutes, échanges ouverts trente minutes, cinq demandes simultanées par joueur. Les pauses et gels administrateur bloquent les accords, tout en permettant l’annulation.

La migration `20261022190018_direct_trades_chest_rewards.sql` complète les droits serveur sans exposer les tables d’échanges ou les fonctions privées. Les tests vérifient notamment les rejouements, les réservations, les changements de version, les transferts, les échecs atomiques, les délais et la conservation de l’économie.

## Cartes de démonstration et cercle fermé
Le marché noir exige désormais une carte active. Aucune carte n’est attribuée automatiquement aux comptes existants. L’entrée payante est supprimée. Le joueur dépose une candidature ou saisit un code donnant directement la carte configurée. Les anciennes cartes sont conservées, sans nouvelle facturation. L’administrateur peut attribuer gratuitement la Basique, Premium, Gold, Platine, Diamond ou Cosmic depuis Administration → Marché noir → Cartes et accès des joueurs. Chaque joueur possède une carte active à la fois ; le remplacement, la suspension, la réactivation et le retrait sont audités.

Chaque gamme possède ses réglages : accès au marché, autorisation d’achats fictifs, taux exact facultatif en euros par diamant, minimum et maximum par transaction, montant quotidien UTC et limite hebdomadaire par joueur. Minimum et maximum identiques imposent un montant exact. Un taux vide reprend celui du serveur. La Cosmic accepte jusqu’à 90 milliards d’euros fictifs pour son taux et ses limites par transaction/jour ; ses propres limites remplacent les plafonds standards. Le gel et le plafond total global restent prioritaires. Les autres cartes conservent leurs limites standards. Les dépenses de la semaine suivent le joueur, même après remplacement ou retrait de carte. Une modification administrative invalide les devis précédents. Les reçus déjà validés restent rejouables sans distribuer de nouveaux diamants.

Les cartes ont six animations CSS distinctes, désactivées avec la réduction des mouvements. L’interface montre la carte attribuée et les conditions des autres gammes. Les coffres scellés restent achetables/ouvrables sans adhésion ; les annonces, achats de diamants et échanges directs requièrent une carte active. Les annulations restent possibles après suspension/retrait, sans bloquer les objets réservés. Les cartes sont fictives et ne contiennent aucune donnée bancaire.

## Mode invité, gestion des comptes et nouvel achat des coffres
Le formulaire d’entrée propose par défaut « Jouer en invité » avec seulement un pseudo unique. Le service Edge `ct-accounts` crée un compte Auth de démonstration avec identifiant technique interne, un secret aléatoire dérivé côté serveur et une session normale sauvegardée dans le navigateur. Aucun mot de passe ni e-mail n’est demandé à l’invité. Un nonce de tentative conservé temporairement permet de reprendre une réponse réseau perdue sans créer un deuxième compte ou une deuxième prime. Le mode natif Supabase anonymous n’est pas activé : les comptes invités sont marqués par une métadonnée d’application administrée côté serveur. Les créations sont limitées par empreinte d’origine et par heure, avec un budget global ; aucune adresse IP brute n’est stockée.

L’accès invité dépend de la session de ce navigateur. Pour une récupération durable, l’invité peut transformer lui-même son compte depuis Paramètres : ajouter son adresse, confirmer le lien reçu puis définir son mot de passe. Le même identifiant Auth est conservé, avec crédits, titres, coffres, diamants et carte. Un admin peut également associer une adresse à sa fiche. Administration → Joueurs propose le pseudo, l’e-mail privé, la correction des victoires/défaites/égalités, mises, retours, records et coffres ouverts, ainsi que l’envoi d’un lien de réinitialisation. Les mots de passe existants ne sont jamais lus ni affichés. Les modifications Auth utilisent exclusivement le service Edge, un contrôle de rôle serveur, une comparaison de l’adresse attendue et un journal de demandes idempotentes. La réinitialisation passe par la messagerie Supabase Auth déjà configurée et arrive sur `/settings` pour choisir un nouveau mot de passe.

Les statistiques corrigées sont enregistrées comme écarts audités par rapport aux résultats réels. Les profils et classements permanents les prennent en compte ; les nouveaux résultats continuent de s’y ajouter. Les transactions, les parties d’origine et les récompenses de quêtes ne sont pas réécrites. Les classements hebdomadaires restent fondés sur les événements effectivement enregistrés pendant la semaine. Les soldes continuent d’être gérés par les ajustements comptables existants.

Tous les coffres s’achètent maintenant depuis Coffres/Boutique avec « Acheter le coffre ». L’achat, les réductions, les stocks et les limites par joueur sont contrôlés avant d’ajouter le coffre à l’inventaire ; aucun titre n’est révélé à ce stade. L’ouverture ultérieure ne paie pas une deuxième fois et ne consomme pas deux fois le quota. Les coffres événementiels et les offres gratuites sont compatibles. Le marché noir ne vend plus de coffres neufs : il sert uniquement aux annonces et échanges entre joueurs disposant d’une carte d’accès. Les probabilités sont figées à l’achat ; les anciens inventaires restent utilisables.

## Admissions du cercle fermé
Administration → Marché noir → Cartes et accès des joueurs → Candidatures et codes d’accès : demandes en attente/acceptées/refusées, acceptation avec choix parmi les six cartes, refus avec message au joueur. Une candidature par jour et une seule en attente par compte. Les décisions et attributions sont atomiques, idempotentes et auditées ; aucune écriture de crédit n’est générée.

Les codes ont un nom interne, une carte, un quota total, une date d’expiration et un interrupteur actif. Le code est choisi ou généré aléatoirement par l’administrateur puis transmis au joueur ; seule son empreinte SHA-256 est stockée. Le code brut n’est ni journalisé ni conservé dans les tentatives locales. L’écran admin montre les 100 derniers codes, leur consommation et leur statut. Les demandes sont paginées par 50. Les tentatives de codes invalides consomment le budget serveur de 30 opérations par minute. Un compte possédant une carte active peut recevoir un code de carte personnalisée ; les suspensions nécessitent toujours une intervention admin. Le retrait d’une carte ne remet pas à zéro les utilisations d’un code par ce joueur.

## Limites hebdomadaires des cartes
Le champ administrateur « Total par joueur » devient « Limite hebdomadaire par joueur » pour les six cartes, en conservant les montants existants (vide = sans limite hebdomadaire). La semaine court du lundi 00:00 au lundi suivant 00:00 en Europe/Paris, y compris lors des changements d’heure. La boutique de diamants affiche la consommation de la semaine, le plafond et la date/heure précise du prochain renouvellement. Le catalogue des cartes et le panel admin affichent la même échéance calculée côté serveur. La remise à zéro est calculée depuis les reçus, sans tâche planifiée ni suppression d’historique ; les jours et le plafond global du serveur conservent leur comportement. Remplacer, retirer ou réattribuer une carte ne remet pas la consommation hebdomadaire à zéro. Le nom SQL historique lifetime_cents est conservé uniquement pour compatibilité des RPC administratives ; il représente désormais ce plafond hebdomadaire.

## Coffres en masse et inventaire regroupé
La fenêtre de coffre affiche les chances exactes dans huit cartes de rareté et une barre de répartition. Le joueur choisit une quantité de 1 à 100 (raccourcis 1/5/10/25/100) et confirme le montant total. Le RPC ct_buy_chests valide le prix et l’offre, le stock, les quotas et le solde ; tous les exemplaires et le débit unique sont validés ensemble ou annulés ensemble. Rejouer le reçu ne crée aucun exemplaire supplémentaire. Les probabilités restent indépendantes pour chaque coffre, sans garantie de rareté liée à la quantité.

Inventaire → Vos coffres propose Regroupés / Par case et un tri par date, nom, rareté ou quantité. Les groupes réunissent les mêmes définitions, noms et probabilités ; les exemplaires restent distincts côté serveur. Le compteur affiche par exemple Coffre mythique ×10, avec les disponibilités et réservations. Ouvrir ou vendre depuis le groupe sélectionne un exemplaire disponible ; les coffres réservés ne sont jamais proposés par ces boutons.

## Codes promo avec coffres personnalisés
Administration → Codes promo → Coffre offert propose tous les coffres standards et personnalisés/événementiels créés dans Coffres, y compris les définitions avec stock ou calendrier. Un code peut offrir 1 à 5 exemplaires avec ses autres récompenses. À la réclamation, le serveur vérifie l’activation, les dates, le stock total et le quota du joueur, puis fige les probabilités et la sélection de titres dans chaque exemplaire. Les cadeaux consomment le stock et comptent dans le quota du coffre, sans débit de crédit ni consommation d’une réduction commerciale. Toute erreur annule également les autres récompenses et l’utilisation du code. Les anciens reçus restent rejouables sans nouvelle distribution.

## Conversion par carte, canal privé et ventes en masse
Le réglage global crédits → diamants doit être actif ET la carte attribuée au joueur doit porter credit_conversion_allowed. Les cartes et anciens codes démarrent avec cette permission désactivée. Administration → Marché noir → Cartes permet de l’activer sans remplacer la carte, ou lors de l’attribution/acceptation d’une candidature. Le créateur de code d’accès peut inclure la permission ; seuls les bénéficiaires de ce code la reçoivent. Les suspensions, le gel global et la fermeture du marché bloquent les nouvelles conversions, sans empêcher la reprise d’un reçu déjà validé. Le taux exact est confirmé avant la dépense.

Le premier onglet du marché noir est le canal privé Actualités du cercle : annonces, événements et offres administrateur, lecture réservée aux membres actifs. Les admins peuvent publier plusieurs messages, les modifier ou les masquer, avec justification et historique d’audit. Les pages de trente messages utilisent un curseur et les textes sont échappés par React.

Vendre & échanger propose une quantité de coffres identiques disponibles : jusqu’à vingt annonces actives par joueur (limite existante). Une action publie une annonce indépendante par exemplaire au prix unitaire indiqué. Le stock d’objets, les réservations, les droits et le plafond sont vérifiés dans la même transaction ; aucun lot partiel n’est publié et les tentatives répétées ne doublent pas les annonces. Les champs de destinataire et d’objet demandé s’appliquent à chaque annonce.

## Tarifs de gros et assistance privée
Boutique de coffres : 2 % de remise dès 10, 3 % dès 50, 5 % dès 100 dans un même achat, sans cumul avec les promotions. Le serveur calcule le total arrondi en crédits entiers et exige sa confirmation. La somme des prix enregistrés sur chaque exemplaire est exactement égale au débit. Le stock et les quotas comptent toujours les exemplaires, pas les lots.

Marché noir → Achats en gros permet de réserver 2 à 1 000 coffres identiques et définir 1 à 8 paliers de prix unitaires en diamants. Chaque seuil doit être plus élevé que le précédent et son prix ne peut pas augmenter. Les prix du palier choisi s’appliquent à toute la quantité achetée dans cette transaction. Le vendeur garde ses exemplaires réservés jusqu’à vente, annulation ou expiration à sept jours. Les réservations s’appliquent à l’ouverture, aux ventes individuelles et aux échanges directs. L’achat transfère tous les exemplaires et les diamants ensemble ; un reçu répété ne distribue rien de plus. L’administration peut annuler une offre avec justification, et le vendeur peut annuler même après retrait de sa carte.

Paramètres → Contacter un administrateur : tickets privés par catégorie (Marché noir, compte, coffres, problème technique, autre), conversation, réponses administrateur, fermeture et réouverture. Cinq tickets ouverts maximum, messages de 4 000 caractères, historique paginé par cinquante messages et cinq cents messages maximum par discussion. Administration → Tickets & support contient la boîte de réception, les filtres et les réponses avec justification. Les requêtes contrôlent l’identité du propriétaire ou le rôle admin côté serveur. Les messages ne sont pas ajoutés au journal d’audit général ; seuls les références et actions y figurent. Aucun e-mail automatique n’est envoyé : les réponses sont consultables dans les paramètres.

## Cartes personnelles et réinitialisation des plafonds
Les gammes hors Cosmic ont une limite hebdomadaire finie, au plus égale à six plafonds quotidiens. Les valeurs existantes qui dépassaient cette règle sont ramenées à six jours ; la Cosmic est toujours sans limite hebdomadaire. La limite effective tient compte du plafond quotidien réellement applicable au joueur.

Administration → Marché noir → Cartes → rechercher le joueur → Personnaliser la carte et gérer les plafonds : quatre textes (bandeau, nom, ligne de code, pied), deux couleurs de fond, couleur du texte, dix animations dont le mode immobile, taux exact, minimum/maximum d’achat, limite quotidienne, limite hebdomadaire et autorisation d’achats fictifs. Un champ vide hérite de la gamme ; une limite spéciale de transaction/jour remplace le plafond standard pour ce joueur. Les gels et le plafond total du serveur restent prioritaires. L’apparence ne modifie jamais la gamme réelle ni les permissions administrateur. Un aperçu est affiché avant enregistrement.

La création d’un code d’accès propose le même modèle personnalisé, qui est attribué aux bénéficiaires du code avec l’autorisation de conversion choisie. Couleurs strictement hexadécimales, animations sur liste autorisée, textes bornés et affichés comme texte par React. Aucune personnalisation n’est modifiable par un utilisateur ordinaire.

L’admin peut réinitialiser le compteur du jour, de la semaine ou les deux, après confirmation et justification. Cela enregistre un nouveau point de départ des consommations, sans modifier les achats, les crédits, les diamants, les statistiques ou les reçus. Les nouvelles acquisitions utilisent un horodatage serveur ordonné après la remise à zéro ; le changement de carte ne remet pas implicitement les compteurs à zéro. Les reçus précédemment validés restent rejouables sans nouvel achat.

Le solde de diamants affiche son équivalent fictif en euros sous le montant dans le marché et la boutique de diamants, au taux effectif de la carte. Le calcul et l’arrondi au centime utilisent des entiers de précision arbitraire côté navigateur, y compris pour les très grands soldes. Il s’agit d’une valorisation de démonstration, sans retrait en argent réel.

Un membre disposant déjà d’une carte active peut utiliser un code personnalisé depuis Marché noir → Activer une carte personnalisée avec un code, après confirmation du remplacement. L’inventaire, les soldes, les achats et les points de départ des compteurs sont conservés. Un code standard ne remplace pas une carte existante et aucun code ne permet de contourner sa suspension.
